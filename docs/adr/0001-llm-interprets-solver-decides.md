# ADR-0001: The LLM interprets, the solver decides

- **Status:** Accepted
- **Date:** 2026-11-25
- **Related:** [04 §4 Algorithms](../04-technical-architecture.md#4-algorithms) · [02 §1](../02-ai-features.md#1-overview) · [ADR-0003](0003-schema-constrained-workflows-not-agents.md) · [ADR-0005](0005-offline-twin-graceful-degradation.md)

## Context

Calendar decisions mix hard constraints with soft trade-offs. The hard constraints are working hours across zones, DST changes, national holidays, nobody double-booked, and minimum notice. The soft trade-offs are fairness across zones, focus time, daily load and preferences. Breaking a hard constraint is a visible, trust-destroying error, and research says trust is the bottleneck for this product ([01 §1](../01-user-research.md), insights I4 and I10).

LLMs are good at language: intents, names, relative dates, briefs, tone. They are not a reliable place to do interval and time-zone arithmetic. Their output is non-deterministic, and it is hard to unit-test or to explain with numbers. We also need:
- every suggestion to be checkable and explained by numbers the user can see;
- the demo to run with no API key;
- slot search within the latency NFR (p95 < 300 ms).

## Decision

Split the work by what each part is good at.
- **Claude (`claude-opus-5-5`) handles language only.** It turns a sentence into a typed `ParsedCommand`, writes a `MeetingBrief` from computed facts, and polishes a `Draft` on request ([gateway.py](../../services/api/app/ai/gateway.py), [assistant.py](../../services/api/app/services/assistant.py), [briefs.py](../../services/api/app/ai/briefs.py)).
- **Deterministic engines make every decision** ([engines/](../../services/api/app/engines/)). They choose times, rank conflict fixes, plan reminders, and compute analytics, forecasts and insight cards.
- **The LLM never returns a time and never sees free/busy data.** Deterministic code resolves the parsed names and event references, and turns the window, duration and limits into a `SlotRequest` for the scheduler.
- **Explanations come from engine state.** Reasons, warnings, priority factors and the model card are generated by the code that produced the score. The LLM only words briefs and drafts.

## Consequences

**Positive**
- Hard constraints are property-tested: Hypothesis checks 40 random requests per run and has found no violation. Conflict fixes reuse the scheduler, so they cannot create a new double-booking, and tests check every option.
- An explanation cannot drift from its ranking, because both come from the same components.
- Scheduling is fast and needs no LLM call: 135–331 candidates in 2–42 ms on this machine.
- The product works offline ([ADR-0005](0005-offline-twin-graceful-degradation.md)). LLM nondeterminism is confined to interpretation, which the user sees as chips before anything changes.

**Negative**
- Kairos can only do what an engine supports. Requests outside the 10-action schema get help or a clarifying question, and multi-step requests need several commands.
- Ranking quality rests on hand-tuned weights (fairness .24, focus .22, …) until F8 learning and real data recalibrate them.
- Intent semantics live in two places, the parse schema and the engines that consume it, and they must evolve together.

## Alternatives considered

| Option | Why not (now) |
|---|---|
| The LLM proposes times directly from a free/busy dump | Hallucinated or DST-wrong slots with no guarantee; large prompts full of personal data; slow and costly |
| The LLM re-ranks engine-generated candidates | Rankings would stop matching a reproducible score, and testing gets harder. Worth revisiting only for subjective tie-breaks, behind an eval |
| An agent with calendar tools that books on its own | Less predictable and auditable ([ADR-0003](0003-schema-constrained-workflows-not-agents.md)); reserved for the external agent, F11 |
| No natural language, forms only | Loses F6 and much of the P1 value. The schedule-assistant form exists anyway as the structured path |
